# AI Coding Rules

이 문서는 ParkWith 개발 시 항상 적용할 기본 코딩 규칙만 정리합니다.

위치, 배터리, 개인정보, MVP 경계처럼 특정 상황에서만 필요한 상세 규칙은 `.codex/skills/playmate-location-safety`로 분리합니다.

## 기본 원칙

1. 문서에 정의되지 않은 기능을 임의로 추가하지 않는다.
2. MVP 범위를 벗어나는 기능은 사용자 확인 없이 구현하지 않는다.
3. 하나의 파일에 과도하게 많은 책임을 넣지 않는다.
4. 화면, 비즈니스 규칙, API/저장소 코드를 섞지 않는다.
5. 임시 코드, 사용하지 않는 변수, 함수, 패키지를 남기지 않는다.
6. 복잡한 기능은 작은 use case 단위로 나누어 구현한다.
7. 코드를 수정한 경우 관련 문서도 함께 갱신한다.

## 코드 작성 전 확인

- 이 기능이 MVP에 포함되어 있는가?
- 기존에 유사한 기능이나 컴포넌트가 있는가?
- 어느 feature, 화면, 데이터 모델에 속하는가?
- 테스트 가능한 구조인가?
- 공통화가 정말 필요한가, 아니면 feature 내부에 두는 게 나은가?

위 질문에 답할 수 없으면 먼저 짧은 구현 계획을 세운 뒤 코드를 수정한다.

## 폴더 구조 규칙

Flutter feature는 다음 구조를 기본으로 한다.

```text
feature_name/
├─ data/
├─ domain/
├─ presentation/
└─ README.md
```

역할:

- `presentation`: 화면, 사용자 입력, 표시 상태
- `domain`: 비즈니스 규칙, 모델, use case, repository 인터페이스
- `data`: API, DTO, cache, repository 구현체

## 네이밍 규칙

- Flutter 파일명은 소문자와 언더스코어를 사용한다.
- NestJS 폴더명은 소문자와 하이픈을 사용한다.
- 화면 파일은 `*_screen.dart` 형식으로 작성한다.
- 재사용 위젯은 `*_card`, `*_button`, `*_list_item`처럼 역할이 드러나게 작성한다.
- API 관련 파일은 `*_api`, 저장소 관련 파일은 `*_repository`로 구분한다.
- 변수명은 축약어를 남발하지 않는다.

나쁜 예:

```text
usrLoc
tmpData
doThing()
```

좋은 예:

```text
userLocation
selectedVenue
createTripRoom()
```

## 상태 관리 규칙

- 화면 안에서만 쓰이는 단순 상태는 로컬 상태로 관리한다.
- 여러 화면에서 공유되는 상태는 전역 상태 관리 도구를 사용한다.
- 서버에서 가져온 데이터는 캐싱 전략을 고려한다.
- 비즈니스 상태와 단순 UI 상태를 섞지 않는다.

## 에러 처리 규칙

사용자에게 기술적인 에러 메시지를 그대로 보여주지 않는다.

나쁜 예:

```text
NullPointerException
Network Error 500
```

좋은 예:

```text
현재 정보를 불러오지 못했어요. 잠시 후 다시 시도해주세요.
요청을 처리하지 못했어요. 다시 시도해주세요.
```

## 테스트 규칙

기능을 추가할 때 최소한 다음을 확인한다.

- 화면이 정상적으로 열리는가?
- 빈 데이터일 때 화면이 깨지지 않는가?
- 네트워크 실패 시 에러 처리가 되는가?
- 사용하지 않는 코드가 남아 있지 않은가?

위치, 배터리, 개인정보와 관련된 테스트는 `.codex/skills/playmate-location-safety`를 참고한다.
